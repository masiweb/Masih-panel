# پشتیبان‌گیری و بازیابی قابل‌انتقال Masiha VPN

این راهنما برای جابه‌جایی از سرور قدیمی به سرور تازه، **با یا بدون تغییر دامنه و IP** است.
سیستم بازطراحی‌شده از فایل رمزگذاری‌شده‌ی `masiha-full-*.tar.gz.gpg` (فرمت نسخه ۱ و ۲) پشتیبانی می‌کند.

## ساخت بکاپ از داخل پنل

در «پنل مسیحا ← پشتیبان‌گیری و بازیابی» یکی از دو حالت انتخاب می‌شود:

- **کامل**: همه جدول‌های SQLite و فایل‌های سرویس (گواهی‌های VPN، رسانه و کش Local Telegram Bot API)؛ فضای کافی لازم است.
- **سبک**: دیتابیس خرید/کیف پول/حساب‌ها، اما بدون محتوای کتابخانه رسانه و کش حجیم Telegram Bot API؛ برای مهاجرت کامل رسانه مناسب نیست.

پس از پایان، فایل GPG و فایل کلید `backup-secret.key` را در دو محل امن دانلود و نگهداری کنید. بکاپ با AES-256 رمزگذاری و همراه هش SHA-256 ثبت می‌شود. در نسخه جدید جریان tar/gzip به GPG متصل شده و فایل gzip رمزنگاری‌نشده‌ی حجیم به‌عنوان نسخه موقت دوم ساخته نمی‌شود.

**مهم:** بکاپ آنلاین یک Snapshot است؛ اگر مبدأ همچنان سفارش، تراکنش یا پیام جدید بپذیرد، مهاجرت قطعی به یک Snapshot نهایی پس از توقف کنترل‌شده نویسنده‌ها نیاز دارد.

## بازیابی روی سرور جدید

1. نرم‌افزار مسیحا را روی سرور جدید نصب کنید و **ابتدا دامنه مقصد و گواهی HTTPS همان دامنه** را فعال کنید. برای مثال مقصد `s3.chanelchat.ir` و مبدأ `s2.chanelchat.ir`.
2. در پنل جدید به «پشتیبان‌گیری و بازیابی» بروید و فایل GPG و کلید را بارگذاری کنید (محدودیت ۶ گیگابایت؛ فضای کافی برای رمزگشایی لازم است).
3. برنامه ابتدا فایل را رمزگشایی و بررسی می‌کند، تاریخ و دامنه مبدأ و مقصد را نشان می‌دهد.
4. پس از تأیید کلمه `RESTORE`، **بازیابی قابل‌انتقال** اجرا می‌شود. این حالت با بازیابی کامل ماشین قدیمی متفاوت است.
5. بکاپ برگشت روی **سرور مقصد** در مسیر `/root/masiha-backups/portable-rollback-YYYYMMDDTHHMMSSZ` باقی می‌ماند.

### چه چیزهایی از مقصد حفظ می‌شود؟

- دامنه مقصد، فایل تنظیمات اصلی `/etc/masiha-vpn-extension/config.json`، SSL/Let's Encrypt، Nginx و مسیرهای پنل/ساب
- باینری نصب‌شده‌ی 3x-ui/Xray و نسخه سرویس‌های سیستمی جدید
- اعتبارنامه ورود مدیر پنل مقصد و شناسه امن نشست‌های آن
- اینباندهای جدید مقصد؛ اینباندهای منبع با پورت تکراری روی پورت آزاد قرار می‌گیرند

### چه چیزهایی از بکاپ منتقل می‌شود؟

- دیتابیس پنل: حساب‌ها، کلاینت‌ها، سهمیه و مصرف، نودها و اینباندهای قدیمی
- دیتابیس افزونه: کاربران VPN، مجوزها و اطلاعات موردنیاز
- دیتابیس فروش: کاربران، کیف پول، سفارش‌ها، چت‌ها و آرشیو رسانه در بکاپ کامل
- کلیدها و گواهی‌های OpenVPN و احراز هویت OpenConnect، فایل‌های IPsec، اثرانگشت موسیقی و فایل‌های قابل‌انتقال Telegram API
- لینک اشتراک‌های ذخیره‌شده با **دامنه و مسیر ساب مقصد** بازسازی می‌شوند؛ لینک‌های پروتکل کش‌شده کنار گذاشته می‌شوند تا برنامه آن‌ها را دوباره از پنل بسازد

### مواردی که عمداً خودکار روشن نمی‌شوند

- پردازشگرهای Telegram و زمان‌بندهای موزیک/فیلم/AI: تا وقتی مبدأ فعال است، اجرای هم‌زمان آن‌ها می‌تواند پیام و سفارش تکراری ایجاد کند.
- نودهای خارجی واردشده از بکاپ: برای جلوگیری از دو کنترل‌کننده هم‌زمان ابتدا غیرفعال می‌شوند؛ پس از بررسی هر نود مجدداً فعال کنید.
- پورت‌های قدیمی که با Nginx، OpenConnect یا اینباندهای مقصد تداخل دارند: به پورت دیگری نگاشت می‌شوند. **پورت‌های جدید در کلاینت‌ها و تونل‌ها باید واقعاً تست شوند.**
- گواهی‌های TLS مخصوص ماشین قدیمی روی HTTPS مقصد بازنویسی نمی‌شوند.

## مراحل نهایی پس از انتقال

1. صحت تعداد کاربران، مانده‌ها، لاگ مصرف، فایل‌ها و لینک اشتراک را روی مقصد تأیید کنید.
2. یک اتصال واقعی VLESS/Trojan و در صورت نیاز OpenVPN/OpenConnect را از شبکه ایران آزمایش کنید.
3. مبدأ را وارد پنجره قطع کنترل‌شده کنید: پردازشگر سفارش، آپلود و ربات را متوقف کنید؛ از آخرین داده‌ها Snapshot نهایی بگیرید و روی مقصد بازیابی کنید.
4. فقط **پس از تأیید توقف پردازشگر مبدأ**، Telegram Local API و پردازشگر مقصد را فعال کنید؛ جلوگیری از دوباره‌پردازش پیام‌ها را بررسی کنید.
5. بعد از تست کامل، DNS/مسیر HAProxy را با مقصد هماهنگ کنید. مهاجرت دیتابیس **به‌تنهایی** به معنی تغییر مسیر تمام کاربرانی که کانفیگ قدیمی دارند نیست.

## روش خط فرمان و تست بدون اعمال

```bash
# اعتبارسنجی به همراه اطلاعات دامنه بدون تغییر فایل‌های عملیاتی
python3 /opt/masiha-vpn-extension/full_backup.py inspect /root/masiha-backups/FILE.gpg --key-file /root/KEY

# فقط ساخت طرح روی کپی دیتابیس‌ها بدون تعویض داده زنده
python3 /opt/masiha-vpn-extension/full_backup.py restore /root/masiha-backups/FILE.gpg --key-file /root/KEY --portable --preview

# بازیابی قابل‌انتقال؛ فقط روی سرور مقصد و با تأیید
python3 /opt/masiha-vpn-extension/full_backup.py restore /root/masiha-backups/FILE.gpg --key-file /root/KEY --portable --confirm-restore
```

تذکر: حالت قدیمی بازیابی مستقیم سرور با همان دامنه هنوز از طریق CLI وجود دارد؛ برای انتقال به دامنه متفاوت صرفاً از `--portable` یا ابزار داخل پنل استفاده کنید.


## به‌روزرسانی پنل موجود روی S3 از Git (بدون نصب مجدد)

**برای سروری که قبلاً VPN Manager روی آن نصب شده است** از نصب‌کننده کامل استفاده نکنید؛
فایل‌های دیتابیس، گواهی HTTPS و تنظیمات نود مقصد باید باقی بمانند.

```bash
cd /root/Masih-panel
git fetch origin
git switch upgrade/3x-ui-v3.11.0-migration
git pull --ff-only origin upgrade/3x-ui-v3.11.0-migration
sudo bash deploy/upgrade-portable-backup.sh --check
sudo bash deploy/upgrade-portable-backup.sh
```

این ارتقا فقط موتور و رابط بکاپ و بازیابی را به‌روزرسانی می‌کند، از فایل‌های قبلی
کپی بازگشت می‌گیرد، نسخه جدید 3x-ui را می‌سازد و بعد از بررسی سرویس را راه‌اندازی
مجدد می‌کند. **هیچ دیتابیس، دامنه، گواهی، کلید شخصی یا سرویس ربات تلگرام جدیدی
به‌صورت خودکار فعال یا جایگزین نمی‌شود.** ساخت Go روی سرور کم‌حافظه می‌تواند
طولانی شود؛ فضای آزاد، حافظه و وضعیت سرویس‌ها را قبل از ارتقا بررسی کنید.

روی S3 نسخه‌های قبلی بکاپ در `/root/masiha-migration/incoming/` قرار گرفته‌اند،
اما برای مهاجرت قطعی **آخرین** بکاپ لازم است؛ بکاپ ۲ نوامبر را روی داده‌های جدیدتر
۵ نوامبر یا داده‌های زنده جایگزین نکنید. استفاده از RESTORE باید بعد از تأیید
اطلاعات تازه، بررسی پورت‌ها/لینک‌ها و توقف کنترل‌شده پردازشگر مبدأ باشد.


### سورس بدون پوشه Git روی سرور مقصد

ممکن است نصب قبلی 3x-ui فقط سورس کامپایل‌شده را در
`/opt/masiha-vpn-build-v3.11.0/src/` نگه داشته باشد و فایل `.git`
در آن وجود نداشته باشد. اسکریپت ارتقای جدید دیگر این را خطای قطعی
نمی‌داند. در این حالت برای احراز نسخه معتبر به‌جای ساخت مخزن جعلی،
شناسه Commit پین‌شده در `source-patch.sha256`، صحت باینری
`x-ui.sha256` و نسخه 3.11.0 بررسی می‌شوند. اگر این شواهد موجود
نباشند، ارتقا پیش از تغییر سرویس‌ها متوقف می‌شود.


### سرور مقصد فاقد سورس Go یا فایل go.mod

برخی نصب‌های سرور مقصد فقط باینری فعال 3x-ui را نگه داشته‌اند و
پوشه سورس اصلی ناقص است. اسکریپت ارتقای جدید در این حالت از پوشه
ساخت جداگانه /opt/masiha-portable-build-v3.11.0/ استفاده می‌کند.
سورس رسمی Commit پین‌شده، patch مسیحا، Go و Node دارای SHA256
تأییدشده، و تمامی وابستگی‌های لازم قبل از لمس سرویس‌های زنده
آماده می‌شوند. مرحله prepare دیتابیس، دامنه، SSL یا ربات را تغییر نمی‌دهد.

پس از دریافت جدیدترین Git روی S3:

```bash
bash deploy/upgrade-portable-backup.sh --check
bash deploy/upgrade-portable-backup.sh --prepare
bash deploy/upgrade-portable-backup.sh --check
bash deploy/upgrade-portable-backup.sh
```

در صورت فقدان سورس، check پیام BUILD_SOURCE_MISSING=YES می‌دهد.
بعد از prepare موفق، باید پیام PORTABLE_BACKUP_BUILD_PREPARED دیده شود.
حداقل ۵ گیگابایت فضای آزاد برای ساخت لازم است. در صورت خطا، پوشه
ساخت جداگانه و کش‌های معتبر را پاک نکنید؛ پس از اصلاح مشکل
می‌توانید مرحله prepare را تکرار کنید.


## انتقال مستقیم بکاپ بین دو سرور از داخل پنل

از تب «پشتیبان‌گیری و بازیابی» در `/xui/panel/sales-bot` گزینه
«انتقال مستقیم بکاپ از این سرور به سرور مقصد» اضافه شده است.

1. در سرور مبدأ حالت **کامل** یا **سبک** را انتخاب کنید.
2. IP سرور مقصد، نام کاربری SSH (معمولاً root) و پورت SSH را وارد کنید.
3. «بررسی اتصال و هویت SSH» را بزنید. اثرانگشت نمایش داده‌شده را با
   دستور `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` روی مقصد
   مقایسه و تأیید کنید (در صورت ECDSA/RSA فایل متناظر را بررسی کنید).
4. رمز عبور SSH را وارد کنید و «ساخت بکاپ و ارسال مستقیم» را بزنید.

عملیات روی **خود سرور مبدأ** و در یک Job مستقل اجرا می‌شود؛ بسته
رمزگذاری‌شده از طریق `rsync` و SSH به مقصد می‌رود و از اینترنت
کامپیوتر کاربر عبور نمی‌کند. ارسال قطع‌شده تا سه بار با `--append-verify`
ادامه پیدا می‌کند. فایل و کلید در مقصد بعد از تأیید SHA-256 به صورت
`/root/masiha-backups/web-imports/<job>.gpg` و `<job>.key` ثبت می‌شوند،
سپس کارگر بررسی بکاپ در مقصد اجرا می‌شود.

پس از تأیید، برای اعمال اطلاعات باید **از داخل پنل مقصد** به‌صورت مجزا
بازیابی را تأیید کنید. تغییر DNS/SSL و روشن‌کردن ربات مقصد خودکار نیست.

### شرایط و امنیت

- روی هر دو سرور `rsync` و OpenSSH نصب و پورت SSH باز باشند.
- برنامه مسیحا روی مقصد نصب یا آپدیت شده و کارگر بکاپ در مسیر
  `/opt/masiha-vpn-extension/web_backup_worker.py` موجود باشد.
- کاربر SSH مقصد باید root باشد یا **sudo بدون رمز** برای دستورات
  لازم داشته باشد. رمز ورود SSH جایگزین مجوز sudo نیست.
- رمز SSH ذخیره دائمی نمی‌شود؛ فقط در حافظه موقت tmpfs تحت `/run`
  با سطح دسترسی 0600 قرار می‌گیرد و کارگر آن را می‌خواند و حذف می‌کند.
  هیچ رمز یا کلیدی به صورت پارامتر فرمان یا در گزارش عمومی وارد نمی‌شود.
- کلید میزبان SSH فقط با تأیید اثرانگشت SHA-256 مدیر پذیرفته می‌شود؛
  تغییر اثرانگشت پیش از ارسال موجب توقف عملیات خواهد شد.
- برای فایل‌های حجیم به فضای آزاد کافی در هر دو سرور نیاز است.
- بکاپ آنلاین Snapshot است: برای انتقال قطعی کیف پول، سفارش‌ها و مصرف
  باید بعداً نویسنده‌های مبدأ را متوقف و آخرین Snapshot را منتقل کنید.

# نصب کامل Masiha VPN Manager روی سرور تازه (۱۱ اکتبر ۲۰۲۶)

این راهنما برای **Ubuntu 24.04 x86_64 تازه و بدون نصب قبلی x-ui** است. نصب موجود را با این اسکریپت ارتقا ندهید. منبع نسخه اجرایی، fork پین‌شده SANAei 3x-ui به‌اضافه `deploy/3x-ui.patch` و سرویس‌های `runtime/` است؛ کد FastAPI قدیمی در `app/` نسخه نصب‌شده تولیدی نیست.

## ۱. پیش‌نیازها

- حداقل پیشنهادی: ۲ vCPU، ۴ GB RAM، ۲۰ GB دیسک؛ دسترسی root/sudo، دسترسی خروجی به GitHub، go.dev، nodejs.org، npm و apt.
- رکورد DNS نوع A برای دامنه جدید (مثلاً `vpn.example.com`) باید به IP سرور برسد؛ TCP/80 جهت دریافت گواهی باز باشد.
- در فایروال میزبان/ارائه‌دهنده: TCP/22 (SSH)، TCP/80 و TCP/443، UDP/1194 (OpenVPN)، TCP و UDP/4443 (OpenConnect)، و TCP/8443 تا TCP/8448 برای شش اینباند پیش‌فرض Xray. نصب‌کننده قوانین UFW را اضافه می‌کند اما UFW را خودکار فعال نمی‌کند؛ فایروال ارائه‌دهنده را نیز بررسی کنید. **پورت‌های مدیریتی 62053 و اشتراک داخلی 2096 را عمومی نکنید.**
- اسکریپت هیچ کلید خصوصی، تنظیمات ربات یا رمز عبوری را از GitHub دریافت نمی‌کند.

## ۲. نصب روی سرور جدید

```bash
sudo apt-get update
sudo apt-get install -y git ca-certificates curl
git clone https://github.com/masiweb/Masih-panel.git
cd Masih-panel
git log -1 --oneline
# شیوه پیشنهادی: نصب تعاملی؛ دامنه و ایمیل در ترمینال پرسیده می‌شوند.
sudo bash deploy/install-ubuntu-24.04.sh

# یا برای اتوماسیون (بدون سؤال):
# sudo env DOMAIN="vpn.example.com" EMAIL="admin@example.com" \
#   PANEL_PATH="/xui/" PANEL_ADMIN_USER="admin" \
#   bash deploy/install-ubuntu-24.04.sh
```

در نصب تعاملی، نام دامنه (با رکورد A که به IP همین سرور اشاره می‌کند) و ایمیل صدور گواهی SSL از شما پرسیده می‌شوند. نصب‌کننده تلاش می‌کند گواهی Let's Encrypt را خودکار با Certbot دریافت کند، سپس تمدید خودکار را برای Nginx و ocserv تنظیم می‌کند. پورت عمومی TCP/80 برای HTTP-01 لازم است. این دستور **تنها روی سیستم تازه** مجاز است؛ اگر `/etc/x-ui/x-ui.db` یا x-ui نصب باشد، برنامه به‌جای بازنویسی آن متوقف می‌شود.

عملیات نصب: دریافت Go 1.27.1 و Node 24.21.0، واکشی upstream از `MHSanaei/3x-ui` در commit `7ef22f94c950ff09f0870e2295fa65ad5968742c`، اعمال patch اختصاصی، typecheck و build؛ نصب وابستگی‌ها و Xray با نصب‌کننده upstream؛ جایگزینی باینری اختصاصی؛ دریافت SSL با Certbot؛ تنظیم Nginx و پنل loopback؛ تولید CA اختصاصی EasyRSA و کانفیگ OpenVPN؛ پیکربندی ocserv؛ **تنظیم خودکار HTTPS Subscription** و ساخت شش اینباند پیش‌فرض با کلید Reality تصادفی؛ فعال‌سازی سرویس مشترک سهمیه/انقضا/ربات. نصب‌کننده در پایان وجود شش اینباند، آدرس اشتراک و سرویس‌ها را بررسی می‌کند.

**بعد از نصب موفق، نصب‌کننده آدرس پنل، نام کاربری و رمز عبور تصادفی را خودکار در همان ترمینال نشان می‌دهد.** برای بازیابی بعدی، همان اطلاعات در `/root/masiha-vpn-initial-login.env` با دسترسی root ذخیره می‌شود:

```bash
sudo cat /root/masiha-vpn-initial-login.env
```

پنل: `https://vpn.example.com/xui/`. پس از ورود، رمز را تغییر دهید؛ در این حالت نسخه root-only فایل `/etc/x-ui/install-result.env` باید نیز با اعتبارنامه جدید هماهنگ شود، چون سرویس فروش برای ورود محلی به پنل از آن استفاده می‌کند. رمز را در Git یا چت نفرستید.

## ۳. تنظیمات نهایی از داخل پنل

۱. **Subscription خودکار تنظیم می‌شود:** Listen IP برابر `127.0.0.1`، Port برابر `2096`، مسیر `/sub/` و URL عمومی `https://vpn.example.com/sub/` است (دامنه واقعی شما جایگزین می‌شود). بعد از نصب فقط لینک یک کلاینت آزمایشی را باز و بررسی کنید.
۲. **شش اینباند بدون مشتری به‌صورت پیش‌فرض ساخته می‌شوند:**
   - `8443/tcp` — VLESS + Reality + TCP (کلید خصوصی/عمومی تصادفی مستقل روی همان سرور)
   - `8444/tcp` — VLESS + TCP + TLS
   - `8445/tcp` — VMess + WebSocket + TLS (سازگاری با کلاینت‌های قدیمی)
   - `8446/tcp` — Trojan + TCP + TLS (سازگاری)
   - `8447/tcp` — VLESS + WebSocket + TLS
   - `8448/tcp` — VLESS + XHTTP + TLS (گزینه مدرن‌تر)
   هر سه حالت TLS از گواهی واقعی دامنه سرور استفاده می‌کنند و WS/XHTTP مسیر تصادفی دارند. اجرای دوباره ابزار ساخت، اینباند موجود را بازنویسی یا تکثیر نمی‌کند. برای جلوگیری از برخورد با Nginx، Reality روی 8443 است نه 443؛ Xray هشدار می‌دهد Reality غیر 443 ممکن است در شبکه‌های فیلترشده شناسایی/مسدود شود. پروتکل‌های WS، VMess و Trojan توسط Xray هشدار قدیمی‌شدن دارند، بنابراین برای اشتراک‌های جدید VLESS XHTTP و Reality اولویت دارند.
۳. در قسمت ربات فروش، توکن BotFather، شناسه مدیران، پلن‌ها، درگاه و شماره کارت را در UI وارد کنید؛ بدون توکن و مدیر ربات فعال نمی‌شود. برای واریز کارت‌به‌کارت، اطلاعات تسویه و تأیید دستی رسید نیز باید تکمیل شوند. در تب **صف ارسال تلگرام** تعداد پیام‌های منتظر و پیام‌های ناموفق دیده می‌شود و مدیر می‌تواند پیام ناموفق را دوباره به صف بفرستد. ربات خطاهای موقت پردازش Telegram update را بدون ثبت آن به‌عنوان پردازش‌شده نگه می‌دارد؛ پیام‌های ناموفق بعد از ۱۶ تلاش به‌عنوان موفق علامت نمی‌خورند.
۴. کاربر جدید را در پنل ایجاد و لینک ساب او را باز کنید. پردازشگر مشترک باید حساب‌های OpenVPN و OpenConnect را برای همان مشتری تولید کند؛ حجم و تاریخ انقضا از اشتراک Xray خوانده می‌شود، نه سهمیه مستقل. فایل OpenVPN و اطلاعات OpenConnect در صفحه اشتراک / VPN Profiles قرار می‌گیرند.

**نکته:** اتصال واقعی از اینترنت خارجی، QR code، فایل‌ها، ترافیک مشترک و دریافت پیام ربات را با حساب آزمایشی بررسی کنید. عبور تست‌های کامپایل جای این تست‌ها را نمی‌گیرد.

### بازیابی از خطای Easy-RSA و تکمیل نصب پس از صدور SSL

اگر پس از دریافت موفق Let's Encrypt، هنگام ساخت گواهی OpenVPN خطای زیر را دیدید:

```text
Option conflict:
'build-server-full' does not support setting an external commonName
```

این خطا مربوط به تنظیم شدن متغیر `EASYRSA_REQ_CN` برای فرمان ساخت گواهی سرور است؛ این متغیر تنها باید هنگام ساخت CA ست شود. **در این مرحله، خود پنل، دیتابیس x-ui، گواهی HTTPS و CA اولیه ساخته شده‌اند؛ نصب‌کنندهٔ سرور تازه را دوباره اجرا نکنید و فایل‌های CA یا دیتابیس را حذف نکنید.**

برای سروری که دقیقاً در همین مرحله متوقف شده است:

```bash
cd ~/Masih-panel/Masih-panel
git pull --ff-only origin main
sudo bash deploy/finalize-ubuntu-24.04.sh --resume
```

این فرمان قبل از هر تغییری وجود فایل‌های لازم، تطابق باینری پنل با خروجی اختصاصی Masiha، تطابق دامنه با Nginx/SSL، و فایل اطلاعات ورود با مالک و مجوز صحیح را بررسی می‌کند. همچنین وجود سرویس extension (نشانگر نصب نهایی) را چک می‌کند و روی نصب کامل‌شده یا غیرمرتبط **متوقف می‌شود**. CA و کلید خصوصی موجود مجدداً ساخته نمی‌شوند؛ فقط گواهی سرور OpenVPN در صورت غیبت ایجاد می‌شود. سرویس x-ui برای بارگذاری باینری اختصاصی restart می‌شود.

پس از موفقیت تست نهایی، آدرس پنل، نام کاربری و رمز تصادفی در همان ترمینال نمایش داده می‌شود؛ اطلاعات در `/root/masiha-vpn-initial-login.env` نیز موجود است. با توجه به اینکه نصب‌کننده رسمی اولیه یک API token روی ترمینال چاپ می‌کند، مرحله تکمیل آن توکن اولیه را نیز باطل و مجدداً صادر می‌کند (توکن جدید در خروجی چاپ نمی‌شود). خروجی‌های نصب شامل رمز یا توکن را عمومی منتشر نکنید. اگر پس از اجرای دستور بالا خطای جدیدی رخ داد، فقط بخش خطا و لاگ‌های بدون رمز/توکن را ارائه کنید.

**محدودیت تست:** صدور واقعی CA، گواهی سرور و CRL با Easy-RSA و شرط محافظت از سرور فعال جداگانه تأیید شده‌اند؛ اجرای end-to-end روی همان سرور تازه هنوز از راه دور تأیید نشده است.

### نصب پس از «Native x-ui administrator persisted in SQLite: PASS» متوقف شد

اگر پس از ساخت گواهی OpenVPN، ایجاد شش inbound و پیام موفقیت تأیید نام کاربری در SQLite، این خطا ظاهر شد:

```text
=== Verify real administrator login before enabling commerce ===
ERROR: initial admin login verification failed
ERROR: Masiha finalization failed
```

**این خطا به معنی شکست صدور گواهی یا ساخت اینباندها نیست**. در نسخه قبلی، اسکریپت بلافاصله پس از `systemctl start x-ui` تلاش می‌کرد وارد HTTP پنل شود؛ systemd ممکن است قبل از آماده‌شدن endpoint ورود، سرویس را `active` اعلام کند. این مرحله همچنین در صورت خطای واقعی سرویس یا ناسازگاری رمز شکست می‌خورد.

در نسخه جدید، `deploy/check-panel-login.py` تا **۹۰ ثانیه فقط endpoint بدون احراز هویت CSRF** را بررسی می‌کند. پس از آماده‌شدن، **تنها یک درخواست ورود با رمز ذخیره‌شده** می‌فرستد تا تلاش‌های تکراری به قفل موقت ورود منجر نشوند. در صورت شکست، وضعیت سرویس و پورت `62053` چاپ می‌شود و نصب ناقص باقی می‌ماند تا بتوان بدون پاک‌کردن CA و SSL ادامه داد.

**برای ادامه نصب نیمه‌تمام** (نه نصب جدید)، در اتصال SSH سرور:

```bash
cd ~/Masih-panel
git pull --ff-only origin main
sudo bash deploy/finalize-ubuntu-24.04.sh --resume
```

از اجرای دوباره `install-ubuntu-24.04.sh`، حذف دیتابیس x-ui، پاک‌کردن PKI یا درخواست دوباره گواهی خودداری کنید. نصب‌کننده اکنون وجود marker امن `/etc/masiha-vpn-extension/.finalize-in-progress` را پیش از پرسیدن دامنه تشخیص می‌دهد و شما را به `--resume` راهنمایی می‌کند.

اگر پس از اصلاح همچنان پنل به HTTP محلی پاسخ نداد، ابتدا **بدون نمایش اطلاعات ورود** وضعیت را بررسی کنید:

```bash
sudo systemctl status x-ui.service --no-pager -l
sudo ss -lntp | grep ':62053' || true
sudo journalctl -u x-ui.service -n 40 --no-pager
```

در گزارش‌هایی که ارسال می‌کنید، رمزها، توکن‌های پنل و جزئیات خصوصی کلاینت‌ها را حذف کنید. `sudo bash deploy/check-panel-login.py` نیز به‌تنهایی می‌تواند تأیید کند که فایل root-only با حساب مدیر زنده سازگار است یا نه.

### مشکل ورود مدیر پس از نصب (فایل اولیه با دیتابیس یکسان نیست)

در آزمون واقعی `exon`، نصب‌کننده قدیمی پیام «Username and password updated successfully» را نشان داده و فایل `/root/masiha-vpn-initial-login.env` را با کاربر `admin` ذخیره کرده بود، اما دیتابیس فعال x-ui هنوز نام کاربری تصادفی ایجادشده توسط نصب‌کننده upstream را داشت؛ بنابراین ورود مدیر ناموفق و به‌علت تلاش‌های تکراری، IP داخلی پنل به‌طور موقت محدود شده بود.

**در نسخه اصلاح‌شده** پس از نصب باینری و قبل از شروع سرویس فروش، اطلاعات مدیر یک بار دیگر **با x-ui خاموش** در دیتابیس ثبت می‌شوند؛ نام کاربری واقعاً از SQLite خوانده و کنترل می‌شود؛ پس از شروع x-ui، درخواست ورود به API محلی با اطلاعات فایل محفوظ انجام می‌شود. سپس دسترسی به API احراز هویت‌شده بررسی و فقط **بعد از موفقیت این آزمون و سلامت تمام سرویس‌ها** آدرس پنل، نام کاربری و رمز یک‌بار در خروجی ترمینال نمایش داده می‌شوند. همچنین اطلاعات اولیه در فایل `0600` زیر حفظ می‌شوند:

```bash
sudo cat /root/masiha-vpn-initial-login.env
```

اگر سرور **تازه و هنوز بدون مشتری** است و از نسخه قبل اطلاعات ورود نادرست ذخیره شده، **نصب تازه را تکرار نکنید**. ابزار بازیابی جداگانه را از GitHub تازه دریافت و اجرا کنید:

```bash
cd ~/Masih-panel
git pull --ff-only origin main
sudo bash deploy/repair-panel-login.sh
```

این ابزار فقط روی پنلی با یک مدیر و بدون حساب مشتری اجرا می‌شود، از دیتابیس و فایل‌های اصلی نسخه پشتیبان می‌گیرد، رمز جدید تصادفی را ثبت و در دو فایل داخلی همسان‌سازی می‌کند، پنل و سرویس فروش را راه‌اندازی و **ورود واقعی و موفق به x-ui** را آزمایش می‌کند. آدرس و محل بازیابی رمز را نمایش می‌دهد و در یک ترمینال SSH تعاملی، نام کاربری و رمز جدید را نیز پس از موفقیت چاپ می‌کند. اگر شرایط ایمنی برقرار نباشد، متوقف می‌شود. برای سرور دارای مشتری، بازیابی اختصاصی با نسخه پشتیبان و هماهنگی اعتبارنامه سرویس فروش لازم است.

توجه: چون سرویس فروش از اعتبارنامه محلی استفاده می‌کند، هنگام تغییر رمز مدیر از داخل پنل باید هماهنگی آن با فایل داخلی سرویس فروش نیز حفظ شود؛ تغییر یک‌طرفه می‌تواند عملکرد خرید و ساخت حساب را قطع کند.

### خروج بی‌صدا پس از `=== Checking source patch integrity ===`

اگر پیام‌های `Masiha patch is already fully applied; source is ready.` و `=== Checking source patch integrity ===` را می‌بینید و بدون هیچ خروجی خطایی فوراً به `root@ubuntu:...#` برمی‌گردید، **patch اختصاصی نصب شده اما build متوقف شده است**. در نسخه قبلی یک `git diff --check` اضافی با timeout اجرا می‌شد؛ این دستور برای تأیید صحت patch لازم نیست و می‌تواند با خروجی ناموفق یا timeout، زیر `set -e` نصب را بدون پیام مناسب قطع کند. نسخه اصلاح‌شده با یک `git apply --reverse --check` صحت patch را کنترل می‌کند، بررسی تکراری را حذف می‌کند و برای خطاهای دیگر شماره خط و کد خروج ثبت می‌کند.

روی یک سرور تازه که نصب آن هنوز به مرحله ایجاد پنل نرسیده است، از همان checkout GitHub اجرا کنید:

```bash
cd ~/Masih-panel
git pull --ff-only origin main
sudo bash deploy/install-ubuntu-24.04.sh
```

پوشه `/opt/masiha-vpn-build-20261011` را حذف نکنید. انتظار می‌رود پس از `Masiha source integrity verified.`، پیام `=== Preparing frontend dependencies (Node + npm) ===` را ببینید. اگر دوباره نصب بی‌صدا قطع شد، وضعیت آخرین مرحله را با کد خروج و خطای نصب جمع‌آوری کنید:

```bash
sudo bash deploy/install-ubuntu-24.04.sh 2>&1 | tee /root/masiha-installer-debug.log
echo "installer_exit=${PIPESTATUS[0]}"
```

**هشدار:** لاگ نصب ممکن است در پایان شامل رمز/توکن اولیه باشد؛ کل لاگ را به‌صورت عمومی ارسال نکنید. فقط خطوط مربوط به نخستین خطا، بدون اطلاعات محرمانه، کافی هستند.

### توقف پس از `HEAD is now at 7ef22f94` و دانلود frontend

اگر خروجی پس از `HEAD is now at 7ef22f94` بدون خطا و بدون پیشرفت می‌ماند، دانلود سورس و checkout پایان یافته‌اند؛ مراحل بعدی نصب‌کننده **اعمال patch اختصاصی، نصب بسته‌های npm، بررسی TypeScript و ساخت Vite** هستند. در نسخه قبلی هیچ پیام مرحله‌ای پیش از `npm ci` چاپ نمی‌شد و دانلود بسته‌ها ممکن بود مدت زیادی بدون خروجی متوقف بماند.

**نسخه جدید** قبل و بعد از `git apply` پیام وضعیت می‌دهد و `git apply`/بررسی اختلاف را زمان‌دار می‌کند. همچنین در صورت توقف درست بعد از checkout و پیش از اعمال patch، اجرای مجدد **پوشه unpatched سالم را تشخیص می‌دهد و patch را بدون پاک‌کردن پوشه سورس اعمال می‌کند**. اگر سورس نصفه و ناسازگار باشد، بدون تخریب آن متوقف می‌شود.

برای `npm ci` نیز آدرس‌های npm رسمی، `registry.npmmirror.com` و Tencent یکی پس از دیگری امتحان می‌شوند؛ **هر بار حداکثر ۴۲۰ ثانیه** و با پیام پیشرفت هر ۱۵ ثانیه. جزئیات هر تلاش در `/opt/masiha-vpn-build-20261011/npm-ci-attempt-N.log` ثبت می‌شود. checksumها طبق `package-lock.json` همچنان بررسی می‌شوند و فایل قفل تغییر نمی‌کند. پس از موفقیت، `node_modules` موجود همراه hash فایل قفل برای ادامه کار استفاده می‌شود. در صورت نیاز، آدرس اختصاصی npm باید HTTPS باشد و از طریق متغیر `MASIHA_NPM_REGISTRY` تعیین شود.

اگر نصب هنوز بدون پیشرفت است، برای بررسی در اتصال SSH دوم:

```bash
ps -eo pid,ppid,etime,stat,%cpu,%mem,args | grep -E '[n]pm|[g]it apply|[n]ode|[g]o build|[v]ite'
```

برای ادامه نسخه به‌روزشده، نصب قبلی را در همان ترمینال با `Ctrl+C` متوقف کنید. سپس **در مسیر واقعی Git clone پروژه**:

```bash
git pull --ff-only origin main
sudo bash deploy/install-ubuntu-24.04.sh
```

در اجرای مجدد مسیر `/opt/masiha-vpn-build-20261011/src` و cache را حذف نکنید؛ دریافت مجدد کل upstream و بسته‌های سالم لازم نیست. این قابلیت در اسکریپت اضافه شده؛ اجرای نصب کامل روی سرور تازه باید جداگانه تأیید شود.

### خطای Go 403 Forbidden و ادامه ساخت بدون شروع دوباره

اگر بعد از پیغام `vite ... built` خطای `403 Forbidden` برای `proxy.golang.org/github.com/cloudflare/circl` یا `github.com/klauspost/compress` ظاهر شد، بخش React ساخته شده اما Go نتوانسته وابستگی‌هایش را دریافت کند. این **به معنای نصب‌شدن سرویس x-ui نیست**؛ هنوز اطلاعات ورود تولید نشده است.

اسکریپت `deploy/build-3x-ui.sh` اکنون از زنجیره مخازن Go به ترتیب `mirrors.aliyun.com/goproxy`، `goproxy.cn`، `proxy.golang.org` و `direct` استفاده می‌کند. جداکننده `|` عمداً انتخاب شده تا حتی در خطای 403 به آدرس بعدی برود (با `,` این اتفاق برای همه خطاها نمی‌افتد). checksumهای `go.sum` و تأیید پیش‌فرض Go حفظ می‌شوند و غیرفعال نمی‌شوند.

اگر پس از `Building Masiha x-ui Go backend` تعداد زیادی پیام `go: downloading ...` ظاهر شد و خروجی چند دقیقه تغییر نکرد، این مرحله ممکن است در دانلود یکی از **وابستگی‌های فرعی Go** یا در کامپایل پرمصرف CPU باشد؛ پیام `vite ... built` فقط ساخت رابط کاربری را تأیید می‌کند، نه نصب کامل پنل.

در نسخه اصلاح‌شده، علاوه بر دو ماژول بزرگ `cloudflare/circl` و `klauspost/compress` (حداکثر ۱۲۰ ثانیه به‌ازای هر مخزن)، **تمام وابستگی‌های موردنیاز خود باینری** با `go list -mod=readonly -deps .`، پیش از کامپایل، از چند Go proxy دریافت می‌شوند. هر تلاشِ دریافت کل وابستگی‌ها حداکثر **۱۸۰ ثانیه برای هر مخزن** است. کش معتبر قبلی حذف نمی‌شود، `go.sum` و راستی‌آزمایی Go حفظ می‌شود و اگر مخزن اول پاسخ نداد، مخزن بعدی امتحان می‌شود. پس از کامل‌شدن کش، `go build` با `GOPROXY=off` انجام می‌شود؛ پس دیگر وسط کامپایل به اینترنت متصل نمی‌شود. هنگام کامپایل هر **۱۵ ثانیه** پیام پیشرفت دیده می‌شود و watchdog بیست‌دقیقه‌ای وجود دارد. هر دانلود ناموفق اکنون باید خطای قابل‌مشاهده و امکان ادامه پس از تصحیح شبکه داشته باشد.

**این مسیر روی سرور توسعه با checkout پین‌شده واقعی آزمایش شد:** بررسی صحت patch، استفاده مجدد از فایل‌های React، prefetch وابستگی‌ها، کامپایل آفلاین و کنترل SHA256 باینری موفق بودند؛ نصب کامل روی سرور تازه هنوز جداگانه باید آزمایش شود.

برای استفاده از اصلاح، اگر اجرای قبلی هنوز در مرحله `go build` متوقف مانده است، در **همان ترمینال** `Ctrl+C` بزنید و بعد نسخه Git را به‌روز کنید. **پوشه build، کش Go و آرشیوهای Go/Node را پاک نکنید.**

**برای ادامه همان نصب نیمه‌تمام:**

```bash
cd ~/Masih-panel/Masih-panel
git fetch origin main
git switch main
git pull --ff-only origin main
sudo bash deploy/install-ubuntu-24.04.sh
```

در اجرای مجدد اگر `/opt/masiha-vpn-build-20261011/src` قبلاً ساخته شده باشد، ابتدا SHA کامیت پین‌شده و صحت اعمال patch بررسی می‌شود. اگر تطبیق داشت و خروجی کامپایل‌شده رابط کاربری موجود بود، `npm ci` و `vite build` تکرار نمی‌شوند و از همان مرحله Go ادامه پیدا می‌کند. **مسیر ساخت را دستی حذف نکنید.** اگر پوشه سورس با patch مورد انتظار تطبیق نداشته باشد، ساخت به‌جای تخریب اطلاعات متوقف می‌شود.

در صورت نیاز به تعیین مخزن دیگر برای شبکه خاص خودتان:

```bash
sudo env MASIHA_GOPROXY='https://goproxy.cn|https://mirrors.aliyun.com/goproxy|https://proxy.golang.org|direct' \
  DOMAIN='vpn.example.com' EMAIL='admin@example.com' \
  bash deploy/install-ubuntu-24.04.sh
```

در نصب تعاملی نیازی به مشخص‌کردن `DOMAIN` و `EMAIL` در دستور نیست. این fallback مربوط به **وابستگی‌های Go** است و با اولویت IPv4 سپس IPv6 که برای فایل‌های Go/Node پیاده شده تفاوت دارد. ادامه ساخت و fallback واقعی پس از پاسخ 403 در محیط تست تأیید شده‌اند؛ نصب کامل روی سرور نهایی کاربر هنوز تأیید نشده است.

### نصب ناقص و خطای دانلود ۴۰۴

اگر بعد از `apt-get` خطای `curl: (22) 404` دیدید و `x-ui: command not found` یا نبود فایل رمز اولیه را مشاهده کردید، نصب به مرحله ایجاد حساب نرسیده است. فایل رمز را با `nano` دستی نسازید؛ رمز واقعی وجود ندارد.

**راهکار اول (خودکار):** در پوشه صحیح مخزن، `git pull --ff-only origin main` و سپس `sudo bash deploy/install-ubuntu-24.04.sh` اجرا کنید. نسخه جدید، آینه Alibaba را که ۷۰٬۵۵۳٬۹۵۰ بایت خروجی با هش رسمی Go 1.27.1 دارد، پیش از سایت‌های گوگل امتحان می‌کند. checksum SHA-256 در همه حالت‌ها بررسی می‌شود.

**دانلود Node.js و اولویت IPv4/IPv6:** در نسخه اصلاح‌شده، SHA-256 اشتباه Node.js 24.21.0 رفع شده و هش درست `fd8e59d5a511510f6a298afb548f18c7d2b1be404d8b4a27d94fbe49f56cb2d6` است. برای **هر URL** ابتدا `curl -4` امتحان می‌شود؛ اگر دانلود یا بررسی SHA-256 ناموفق بود، `curl -6` همان آدرس را امتحان می‌کند و سپس به آدرس بعدی می‌رود. منابع معتبر موجود شامل Nodejs.org، Nodejs.org/download/release، Alibaba، npmmirror، Tencent و Huawei هستند. منبع Huawei به‌خاطر احتمال timeout در آخر فهرست است. اگر IPv4 موفق شد IPv6 اجرا نمی‌شود؛ اگر هر دو شکست بخورند فایل ناقص پذیرفته نخواهد شد. این اولویت مشخصاً برای **دانلود آرشیوهای Go و Node در این اسکریپت** است، نه تنظیم جهانی IPv6 سرور.

**راهکار دوم (دانلود دستی از آینه جایگزین):**

```bash
curl -fL --retry 3 -o /root/go1.27.1.linux-amd64.tar.gz \
  https://mirrors.aliyun.com/golang/go1.27.1.linux-amd64.tar.gz
echo '63d339f0da5ab53635a56f2490a7984dfe12dfcff22ad749f63edaf590168445  /root/go1.27.1.linux-amd64.tar.gz' | sha256sum -c -
cd ~/Masih-panel/Masih-panel  # مسیر را متناسب با محل واقعی مخزن تغییر دهید
sudo env MASIHA_GO_ARCHIVE=/root/go1.27.1.linux-amd64.tar.gz bash deploy/install-ubuntu-24.04.sh
```

**راهکار سوم (اگر خروجی اینترنت سرور محدود است):** فایل معتبر Go 1.27.1 و در صورت نیاز Node 24.21.0 را از یک سرور قابل‌دسترسی به سرور مقصد با SCP منتقل کنید و از گزینه‌های `MASIHA_GO_ARCHIVE` و `MASIHA_NODE_ARCHIVE` استفاده کنید. برای مثال روی سرور مقصد می‌توانید فایل را از سرور قبلی با `scp root@OLD_SERVER_IP:/opt/masiha-vpn-extension/toolchain/go.tar.gz /root/go1.27.1.linux-amd64.tar.gz` دریافت کنید؛ تنها در صورتی که SSH به آن سرور دارید. **هرگز از checksum صرف‌نظر نکنید.**

اگر هشدار نصب قبلی دریافت شد، اسکریپت را دور نزنید و بدون پشتیبان فایل‌ها را پاک نکنید. نصب کامل روی یک سرور تازه هنوز به‌صورت عملی تأیید نشده است.

## ۶. به‌روزرسانی

آپدیت مستقیم رسمی 3x-ui ممکن است routeهای فروش و OpenVPN/OpenConnect را از باینری حذف کند. برای نسخه اختصاصی تنها از patch داخل همین Git و ساخت مجدد استفاده کنید:

```bash
cd ~/Masih-panel
git pull --ff-only origin main
sudo env MASIHA_BUILD_ROOT="/opt/masiha-vpn-build-next" bash deploy/build-3x-ui.sh
# پس از بکاپ x-ui.db و باینری فعلی و تایید تست‌ها، باینری را با فرآیند تغییر نسخه جایگزین کنید.
```

اسکریپت ساخت عمداً هیچ نسخه موجودی را خودکار بازنویسی یا restart نمی‌کند. برای migration/upgrade از راهنمای مستقل و بکاپ استفاده کنید.

## ۷. محدودیت‌های صادقانه نسخه

- این بسته روی Ubuntu 24.04 amd64 طراحی شده و روی یک کپی تمیز سورس، build و typecheck شده است؛ اجرای installer یک‌پارچه روی سرور **کاملاً تازه** هنوز تست نشده است.

- آدرس فعلی `xu.chanelchat.ir` متعلق به سرور قدیمی است؛ برای سرور جدید بدون تغییر DNS همان دامنه را استفاده نکنید.
